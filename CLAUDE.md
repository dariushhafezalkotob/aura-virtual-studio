# Aura Virtual Studio

Browser-based virtual film studio: design 3D scenes, set up and animate actors, and record camera moves (including using a phone as a gyro camera remote).

## Stack
- React 18 + TypeScript + Vite 6, Tailwind CSS
- Three.js via @react-three/fiber and drei
- @gradio/client for AI model backends
- GitHub: dariushhafezalkotob/aura-virtual-studio

## Run
- `npm run dev` → https://localhost:3000 (HTTPS via basic-ssl, needed for phone sensors). No build step; hot reload as before.
- `npm run build` → `tsc && vite build && npm run build:server` (frontend into `dist/`, server bundle into `dist-server/`)
- `npm start` → production server: serves `dist/` plus the same API on `PORT` (default 3000, `PUBLIC_SCHEME` default https)
- `npm run typecheck` → `tsc` (src) **and** `tsc -p tsconfig.server.json` (server + vite.config). `tsconfig.json` only includes `src`, so server code is checked ONLY by the second one -- run both.
- The API lives in `server/`, not in `vite.config.ts` (49 lines now). Dev and production mount the same `createApiMiddleware` + `attachCameraRemoteWs`.
- Secrets in `.env.local` (not committed); see `.env.example`. Dev passes them through `configureEnv(loadEnv(...))`; production uses the process environment.
- Data on disk: `data/projects.json` (small metadata), `data/blobs/<projectId>/` (keyframes + motion), `data/assets/` (GLB, splat, audio, thumbnails)
- `npm run db:start` / `db:stop` → local MongoDB 8.0.32 from `.mongo/` (MongoDB's own prebuilt macOS binaries, gitignored). Homebrew was a dead end: it demands a full Xcode Command Line Tools reinstall. The app needs a database running for ANY api route now.
- `data/` is NOT in git (2026-09-20). It is ~430 MB of generated models that change on every generation, and projects.json + blobs must move together or a clone gets refs to files that do not exist. Snapshot it with `npm run backup:data` (tar.gz into `backups/`, newest 10 kept). Versions committed before that date are still recoverable from git history.

## Deploy
- Domain `pantilt.app` (registered at Cloudflare 2026-09-20). Its DNS record MUST stay **DNS only (grey cloud)**: behind Cloudflare's proxy every request over ~100s returns 524, and generations take minutes. Assets go through R2's own CDN instead (not wired up yet).
- `deploy/setup-server.sh` — one-time, on a fresh Ubuntu 24.04 box (Node 22, Caddy, ufw, the `aura` user, `/etc/aura.env`). Installs `python3-numpy`/`python3-pillow` because `/api/generate-360-from-image` shells out to `slice_equirect_views.py`.
- `deploy/deploy.sh root@<IP>` — from the Mac: typecheck, build, rsync `dist/` + `dist-server/` + manifest, `npm ci --omit=dev`, restart. Never touches `data/` on the server.
- `deploy/aura.service` (systemd, WorkingDirectory `/srv/aura` because prod.ts resolves `dist/` and `data/` from cwd) and `deploy/Caddyfile` (automatic HTTPS, 900s proxy timeouts, WebSocket upgrades).
- LIVE since 2026-09-20: **https://pantilt.app** on Hetzner CX22 (Falkenstein, `2.28.33.208`, EUR 6.49/mo + IPv4 + backups ≈ EUR 8.40). Ubuntu 24.04, Node 22, Caddy 2.11 (Let's Encrypt), ufw 22/80/443, service user `aura`, app in `/srv/aura`.
- `deploy/setup-mongodb.sh` — MongoDB 8 on the server, **loopback only**, password required, URI written into `/etc/aura.env`. The database is never exposed and 27017 is not opened.
- **`git push` is not a deploy.** Pushing sends code to GitHub; `./deploy/deploy.sh root@2.28.33.208` is what puts it on the server. Deploying from a feature branch is fine and normal here.
- After deploying, the browser keeps the old bundle: a HARD refresh (Cmd+Shift+R) is usually what is missing when "the change is not there". The bundle filename changes every build, so comparing `assets/index-<hash>.js` against the source is how to prove what is actually live.
- Server keys (set 2026-09-21): `GEMINI_API_KEY` and `HF_TOKEN` are in `/etc/aura.env`, so everyone signed in generates on the owner's quota. Set or rotate them with `ssh -t root@<IP> "cd /srv/aura && node dist-server/set-key.mjs gemini|hf"` — it prompts without echo, writes the file AND restarts the service.
- Never put a secret on a command line here. `!!` inside a double-quoted ssh command is zsh history expansion: it pasted the previous command into the middle of a `user-add` call, mangled the password, lost `--owner`, and created the account as a plain user. Editors over ssh failed too (`nano` through a non-TTY runner refuses to start; a dangling quote left the command unrun) — which is why the prompt-based CLIs exist. `stat -c %y /etc/aura.env` is the quickest way to tell whether an edit ever landed.
- `AURA_DAILY_GENERATIONS` (default 20) caps generations per non-owner per UTC day.

- Accounts and crew (2026-09-21):
  - scrypt from `node:crypto` (no bcrypt/argon2 native module). N=32768 costs ~63ms and **maxmem must be raised or scrypt refuses to run** (128*N*r is 33.5 MB, over Node's 32 MB default). Sessions are httpOnly cookies in Mongo with a TTL index; wrong email and wrong password give the same answer and a missing account still pays the hashing cost.
  - Everything under `/api` needs a session except `/api/auth/*`. The client shows LoginView until `/api/auth/me` answers, and project hydration waits for the session or it 401s and silently keeps a stale local copy.
  - The owner adds crew from the CREW panel (workflow screen): username + password + role labels. They sign in with the username and see only the projects they are on. Sign-in accepts email OR username.
  - **Saving is the dangerous part.** A save replaces the projects the browser sent, and a crew member's browser only holds what they can see, so deletion is limited to projects the saver OWNS and an upsert can only match a project they can already open. Blobs file under the project's owner, not whoever recorded the take.
  - Quota: owners uncapped, others `AURA_DAILY_GENERATIONS` (20) per UTC day, incremented atomically, refunded when the route answers 5xx.
- RoomBake UV: the guard is for ROOMS ONLY, and there were two separate things making Smart look broken (2026-09-22). DO NOT re-widen the guard and DO NOT lower the triangle limit.
  - The guard in `loadCustomModel` (`uvMode === 'smart'` keeping the model's own UVs when `hasAnyUv && totalVerts > 3600`) is right for an imported room -- it was removed on 2026-09-21 because "Smart appears to do nothing" and that broke the case it protects, since re-unwrapping over a good interior layout packs worse. But it was applying to objects too, where the model's UVs are exactly what needs replacing, so Smart was a no-op on props. It now requires `viewMode === 'interior'`; exterior bakes always unwrap. Either way `engine.lastUvNote` records the decision and the studio prints it.
  - "Re-pick Smart in the dropdown" was never a real escape hatch: a `<select>` fires no `onChange` when you pick the option already selected. There is now an **UNWRAP NOW** button (`handleForceUnwrap`) that calls `reUnwrapRoom` directly.
  - `smartUnwrapGeometry` fell back to 6-way box projection above **1200 triangles** ("prevent CPU thread freezes"), which is nothing -- any real prop is past it, so Smart gave box projection and the SPLIT LONG SECTIONS checkbox did nothing. Measured: the island unwrap is linear and cheap (6k tris 31ms, 25k 95ms, 86k 220ms, 172k 349ms; worst case a curved surface where every triangle is its own plane). Limit is now `SMART_UNWRAP_TRI_LIMIT = 150000`. Measured on a 6.3k-tri prop with junk UVs: atlas use 52.7% -> 82.8%, overlap 2.8% -> 0.2%.
  - Measuring this is easy and worth doing before touching it: bundle the engine with esbuild (`--external:three`), call `RoomBakeEngine.prototype.smartUnwrapGeometry` on an `Object.create(prototype)` carrying just `config`, then rasterise the UV triangles into a grid and count texels hit once vs twice. No WebGL needed.
  - Primitives are a separate story: three's BoxGeometry maps all six faces onto the same 0-1 square, so `primitiveAssets.ts` now deletes the `uv` attribute before export. With no UVs the guard never applies and RoomBake unwraps them properly.

- Phone remote lag (2026-09-19, diagnosed, NOT fixed): Bluetooth is not an option -- Web Bluetooth only makes the browser a BLE central, a phone browser cannot advertise as a peripheral, and iOS Safari has none of it. The lag is in the send path: `CameraRemoteSocket.send` never checks `ws.bufferedAmount`, so at ~66Hz a brief WiFi stall queues ~20 stale samples that then arrive in a burst (WebSocket is TCP, so one lost packet also blocks everything behind it). Fixes in order: drop the sample when anything is still buffered, then a WebRTC DataChannel (`ordered: false, maxRetransmits: 0`) with the existing relay carrying only the handshake. There is a `ping` in the service but no pong and no RTT readout, so nobody is measuring any of this yet. For Android the best transport is `adb reverse tcp:3000 tcp:3000` over USB (phone opens the pairing URL with `localhost` in place of the IP; `localhost` is a secure context so the gyro APIs still work); `getLocalIpAddress` in vite.config.ts returns the first `en*` interface, so the QR always points at WiFi even when a tether is up.
